# 多管路文件架构与实施计划

## 当前基线

- 当前分支：`feat/multi-pipe`。
- `main` 已包含 `constraint-update` 的单管基线。
- 单管真实 CATIA 全流程已经完成，作为本次多管改造的回归基线。
- 单管入口继续保持 `main_point.py -> main1.py -> main2.py -> main3.py -> main4.py`。
- CATIA 模型不在本次代码修改范围内；模型完成后再进行真实坐标读取和全流程测试。

## 目标边界

同一个 CATIA 模型和同一个 `Route_Point` 容器中，存在多组管路端点。每条管路具有自己的 `pipe_id`、起点、终点、方向点、规格和外半径。程序按固定顺序逐条规划：当前管路必须避开 CAD 障碍物，也必须避开已经确认的管路。所有确认的管路最后汇总到一个多管 HTML，并按管路分别生成 CATPart。

本阶段不做前端规格选择、不做全局联合最优搜索、不复制 `main2.py`、`main3.py`、`main4.py` 的第二套算法，也不读取或修改 CATIA 模型文件。每条管路对外只保留一条路线：搜索内部可以尝试不同策略，但不把多条候选路线当作交付结果。

## 1014 整改契约

以下规则是多管路本轮整改的验收边界：

- `completed` 只表示同时满足：没有硬障碍冲突、没有管间扫掠包络相交、工程化几何有效，并且没有使用工程化 fallback。`allow_hard_conflicts` 只允许用于诊断尝试，不能把硬冲突路线变成完成路线。
- `required_clearance=0.0` 表示不增加额外壁间隙；管外半径仍参与扫掠包络计算。两包络刚好相切（有符号净距为 `0`）可以通过，负净距一律失败。障碍物额外净空、规划额外净空和工程化安全带当前均为 `0 mm`，不得在无解时静默放宽硬障碍。
- 管间检查覆盖已确认路线与当前路线的整条扫掠包络。若起点、终点或硬挂点本身小于两管外半径之和，报告点位冲突并提示检查输入点；不能把该冲突当成普通绕行成功。
- 当前管路遇到冲突时，先在本管路内逐步回退到较早决策层并尝试其他局部方向；回退到起点、挂点或安全边界仍无解时停止。保持 `priority` 固定，不自动换序；需要换序时在结果中说明具体阻塞原因并请示用户。
- 严格路线全部失败时，HTML 仍可保留一条诊断路线（包括硬冲突或折线工程化失败），但该路线必须标记为诊断失败，不能生成 CATPart，也不能写成 `completed`。
- 工程化管径的外径沿全长一致，每个转弯必须是圆弧，并使用同一规定的中心线弯曲半径。若转弯前后直段长度不足以容纳该半径，候选路线失败并触发回退；不得把尖角折线或缩小半径的圆角当作正式实体。
- 若可行通道不足以容纳当前管道外径和当前净空，报告实际局部通道宽度、所需宽度和缺口值；管间并行占用则由两管扫掠包络的有符号净距报告，所需中心距为两管外半径之和加额外净空。

## 文件职责和依赖方向

```text
settings.py
  静态 CAD 路径、规格表、算法参数和单管默认值
        |
pipe_config.py
  PipeInstance / RunConfig、多管 JSON 读取和校验
        |
common_space.py + main1.py
  依据所有端点的联合范围和最大管外半径生成一次共享规划空间
        |
main2.py
  复用现有搜索算法，规划一条管路
        |
route_clearance.py
  已确认管路的扫掠包络和管间净距检查
        |
main3.py
  对一条管路进行工程化重建，并再次检查管间净距
        |
main4.py
  保留单条 CATPart 建模能力
        |
multi_pipeline.py
  按 priority 顺序编排上述步骤，汇总 JSON、HTML、CATPart 和 manifest
```

## 输入约定

多管入口读取一个 JSON 配置。每个管路至少包含：

```json
{
  "pipe_id": "PIPE_01",
  "start": [0, 0, 0],
  "goal": [1000, 0, 0],
  "start_dir": [30, 0, 0],
  "goal_dir": [1030, 0, 0],
  "pipe_spec": "metal_19_05",
  "required_clearance": 0.0,
  "priority": 1
}
```

坐标来自同一个 `Route_Point` 容器。CATIA 点名建议使用稳定前缀，例如：

```text
PIPE_01_START / PIPE_01_GOAL / PIPE_01_START_DIR / PIPE_01_GOAL_DIR
PIPE_02_START / PIPE_02_GOAL / PIPE_02_START_DIR / PIPE_02_GOAL_DIR
```

本次先把坐标读取结果落成 JSON；不会让多管坐标循环写回 `settings.py`，避免后一根管路覆盖前一根。

坐标读取完成后，将点文件与规格配置分开维护，再通过 `--points` 合并运行：

```powershell
python main_point.py --body "Part1(Route_Point)" --multi-output outputs\measured_points.json --no-write-settings
python multi_pipeline.py config\multi_pipe.json --points outputs\measured_points.json --run-id run-001
```

`config\multi_pipe.json` 只维护 `pipe_id`、`pipe_spec`、`required_clearance` 和 `priority` 等工程参数；`--points` 文件维护同名管路的四组测量坐标。两者的 `pipe_id` 必须完全一致，合并时不会修改 `settings.py`。

## 运行顺序

1. 读取并校验 `RunConfig`，确保 `pipe_id` 唯一、端点和方向点完整；同时检查起点、终点和硬挂点之间是否存在明显的管间点位冲突。
2. 计算所有管路端点的联合 X 范围，并用所有管路中的最大外半径生成一次共享规划空间。
3. 按 `priority` 和配置顺序规划第一根管路。
4. 在本管路内部尝试搜索策略和局部回退；对候选导引路线检查障碍物和已确认管路的扫掠包络。
5. 通过导引检查后进行 `main3` 工程化重建，强制生成直线与同半径圆弧，并再次检查障碍物、挂点和管间包络。
6. 只有正式验收通过的路线才登记为已占用路线并进入下一根管路的搜索约束；失败路线不占用空间。
7. 若所有严格候选都失败，保留一条诊断路线供 HTML 复盘，记录失败原因和通道报告，但不生成 CATPart。
8. 汇总所有管路的路线和验证报告，生成一个多管 HTML；仅正式通过的路线才交给 `main4.create_catia_part()`。

第一版采用固定 `priority` 顺序。局部回退和所有候选尝试耗尽后仍无解时，`manifest.json` 必须给出阻塞管路、冲突类型、实际通道宽度、所需宽度和缺口值，并建议换序；程序不自动换序。HTML 的“有一条路线”只证明诊断结果已展示，不证明可以建 CATIA 或完成工程验收。

对应字段落在现有输出中：`pipes[*].blocking_reasons`、
`pipes[*].channel_report`、`pipes[*].input_point_conflicts` 和顶层
`reorder_recommendation`。诊断路线使用 `diagnostic_only=true`，因此不会进入
`reserved` 或 `catia/`。

单管模式仍使用 `settings.py` 中原来的输出路径；多管模式使用独立 `run_id` 目录，避免结果互相覆盖。

## 最小改动原则

- `pipeline.py` 保留为单管入口。
- `main1.py`、`main2.py`、`main3.py` 保留命令行入口，只增加可被多管编排调用的函数或参数。
- `main4.py` 的底层 `create_catia_part()` 复用，不新增 `main4_multi.py`。
- 管间净距放在新文件 `route_clearance.py`，不混入 CAD 截面生成逻辑；有符号净距小于 0 时直接判定包络相交。
- 不提交 `outputs/`、CATPart、CAD 输入和 HTML 运行产物。
