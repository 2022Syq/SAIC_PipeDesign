# 多管路文件架构与实施计划

## 当前基线

- 当前分支：`feat/multi-pipe`。
- `main` 已包含 `constraint-update` 的单管基线。
- 单管真实 CATIA 全流程已经完成，作为本次多管改造的回归基线。
- 单管入口继续保持 `main_point.py -> main1.py -> main2.py -> main3.py -> main4.py`。
- CATIA 模型不在本次代码修改范围内；模型完成后再进行真实坐标读取和全流程测试。

## 目标边界

同一个 CATIA 模型和同一个 `Route_Point` 容器中，存在多组管路端点。每条管路具有自己的 `pipe_id`、起点、终点、方向点、规格和外半径。程序按固定顺序逐条规划：当前管路必须避开 CAD 障碍物，也必须避开已经确认的管路。所有确认的管路最后汇总到一个多管 HTML，并按管路分别生成 CATPart。

本阶段不做前端规格选择、不做全局联合最优搜索、不复制 `main2.py`、`main3.py`、`main4.py` 的第二套算法，也不读取或修改 CATIA 模型文件。

## 文件职责和依赖方向

```text
settings.py
  静态 CAD 路径、规格表、算法参数和单管默认值
        |
pipe_config.py
  PipeInstance / RunConfig、多管 JSON 读取和校验
        |
common_space.py + main1.py
  依据所有端点的联合范围和最大管外半径生成一次共享规划空间
        |
main2.py
  复用现有搜索算法，规划一条管路
        |
route_clearance.py
  已确认管路的扫掠包络和管间净距检查
        |
main3.py
  对一条管路进行工程化重建，并再次检查管间净距
        |
main4.py
  保留单条 CATPart 建模能力
        |
multi_pipeline.py
  按 priority 顺序编排上述步骤，汇总 JSON、HTML、CATPart 和 manifest
```

## 输入约定

多管入口读取一个 JSON 配置。每个管路至少包含：

```json
{
  "pipe_id": "PIPE_01",
  "start": [0, 0, 0],
  "goal": [1000, 0, 0],
  "start_dir": [30, 0, 0],
  "goal_dir": [1030, 0, 0],
  "pipe_spec": "metal_19_05",
  "required_clearance": 20.0,
  "priority": 1
}
```

坐标来自同一个 `Route_Point` 容器。CATIA 点名建议使用稳定前缀，例如：

```text
PIPE_01_START / PIPE_01_GOAL / PIPE_01_START_DIR / PIPE_01_GOAL_DIR
PIPE_02_START / PIPE_02_GOAL / PIPE_02_START_DIR / PIPE_02_GOAL_DIR
```

本次先把坐标读取结果落成 JSON；不会让多管坐标循环写回 `settings.py`，避免后一根管路覆盖前一根。

坐标读取完成后，将点文件与规格配置分开维护，再通过 `--points` 合并运行：

```powershell
python main_point.py --body "Part1(Route_Point)" --multi-output outputs\measured_points.json --no-write-settings
python multi_pipeline.py config\multi_pipe.json --points outputs\measured_points.json --run-id run-001
```

`config\multi_pipe.json` 只维护 `pipe_id`、`pipe_spec`、`required_clearance` 和 `priority` 等工程参数；`--points` 文件维护同名管路的四组测量坐标。两者的 `pipe_id` 必须完全一致，合并时不会修改 `settings.py`。

## 运行顺序

1. 读取并校验 `RunConfig`，确保 `pipe_id` 唯一、端点和方向点完整。
2. 计算所有管路端点的联合 X 范围，并用所有管路中的最大外半径生成一次共享规划空间。
3. 按 `priority` 和配置顺序规划第一根管路。
4. 对候选路线做管间净距检查；通过后进行 `main3` 工程化重建。
5. 对工程化后的圆弧中心线再次做管间净距检查。
6. 将通过的管路登记为已占用路线，再规划下一根。
7. 汇总所有管路的路线和验证报告，生成一个多管 HTML。
8. 复用 `main4.create_catia_part()`，按 `pipe_id` 分别输出 CATPart。

当前版本在每根管路生成候选中心线后，用 `route_clearance.py` 对候选和已登记路线做扫掠包络净距筛选，再接受第一条满足要求的候选；如果当前候选集全部不满足，则记录失败并停止本次运行。这样可以先验证顺序编排和硬净距结果，后续若需要更强的搜索引导，再把已登记路线直接加入 `main2` 的搜索代价模型。

第一版采用固定顺序的顺序规划。顺序会影响结果，因此写入 `manifest.json`。如果某条管路在当前顺序下没有满足净距的候选路线，应明确失败并保留失败原因，不自动降低净距要求。

## 输出约定

```text
outputs/<run_id>/
├── planning_space.json
├── planning_space.html
├── routes_guide.json
├── routes_engineered.json
├── multi_route_engineered.html
├── validation.json
├── manifest.json
└── catia/
    ├── pipe_01.CATPart
    └── pipe_02.CATPart
```

单管模式仍使用 `settings.py` 中原来的输出路径；多管模式使用独立 `run_id` 目录，避免结果互相覆盖。

## 最小改动原则

- `pipeline.py` 保留为单管入口。
- `main1.py`、`main2.py`、`main3.py` 保留命令行入口，只增加可被多管编排调用的函数或参数。
- `main4.py` 的底层 `create_catia_part()` 复用，不新增 `main4_multi.py`。
- 管间净距放在新文件 `route_clearance.py`，不混入 CAD 截面生成逻辑。
- 不提交 `outputs/`、CATPart、CAD 输入和 HTML 运行产物。

## 验证边界

先验证配置校验、单管回归和两个合成中心线的净距正反例，再验证多管输出目录和汇总 JSON。CATIA 模型更新完成后，最后再做真实的多点读取、两管规划、综合 HTML 和多 CATPart 验收。
